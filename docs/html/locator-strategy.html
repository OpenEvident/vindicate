Locator Strategy Reference

How Vindicate turns a live DOM element into a stable, semantic, render-agnostic locator — the tier ladder it walks, how it guarantees uniqueness, how it resolves duplicates, the exact syntax each strategy renders to, and why this approach beats hand-written selectors.

00Core principle — locators are derived, never authored

No selector string is ever invented, hand-picked, or transcribed. The agent captures an element's identity evidence (testid, role, accessible name, id, attributes, container row) from a real browser snapshot; the engine then derives the single best locator from that evidence. One element → one strategy → one verified locator.

The derived locator is a structured value (StructuredLocator) with a strategy, a confidence (high/low), and the fields that strategy needs. That one value is the single source of truth rendered onto three surfaces — so generated code, the live click resolver, and the browser_read badge can never drift apart.

01The pipeline

Derivation happens once, at capture time, inside the browser where the DOM and layout are real. Everything downstream just renders the same structured value.

CAPTURE

Snapshot in the page

deriveStructuredLocator() runs inside page.evaluate. It walks the tier ladder, validating each candidate against the live DOM until one resolves to exactly one element.

CARRY

StructuredLocator on the wire

The chosen {strategy, confidence, …} travels with every element and is cached in the per-session descriptor map, keyed by a stable ref.

RENDER

Three render targets

Codegen → TypeScript page-object line; live resolver → a Playwright Locator for browser_act; browser_read → a [via …] badge so the agent sees how it will resolve.

02The tier ladder

Walked top to bottom. The first tier that resolves to exactly one element wins; a tier that fails its uniqueness check falls through to the next. Higher tiers are more stable and more human-readable, so the ladder is ordered by durability.

Uniqueness check column = the exact guard that must pass for the tier to fire.

T4role_name Role + accessible name, where the name is matchable: an author name (any role) or descendant text on a name-from-content role roleNameUnique across the captured set high

T7scoped A per-row control whose own ref collides — scope it to its uniquely-named container row container row name is unique high

Stability ordering, not preference for its own sake. Test-ids and ids are contract-grade. Role+name mirrors how a user perceives the control, so it survives restyles and DOM reshuffles. Attribute combos and positional indexes come last because they break the moment markup shifts — and nth is flagged low so a human reviews it.

03How duplications are handled

A locator is only valid if it matches exactly one element. Vindicate enforces this at four levels — it never reaches for .first()/.nth() on an ambiguous selector to paper over a collision.

MechanismWhat it doesResult
Per-tier uniqueness gate Every tier above runs a live countByXpath(...) === 1 / uniqueByCss(...) probe against the real DOM before it is allowed to win. A non-unique candidate is rejected and the ladder falls through to the next tier.
roleNameUnique flag Before T4, the engine counts how many captured elements share the same role + name digest. T4 only fires when that count is 1. Two buttons both named “Edit” will not both become getByRole('button',{name:'Edit'}).
Container scoping (T7) When a control’s ref collides (e.g. a “Delete” button repeated per table row) and it has no test-id, the engine finds the nearest repeating-row ancestor with a unique accessible name and scopes to it. getByRole('row',{name:'Product ABC'}).getByRole('button',{name:'Delete'}) — each row resolves to its own control.
Stable ref re-digest A colliding element’s ref is re-hashed with its row anchor (role|name|row:<container>) so each sibling keeps a distinct, stable ref across reads. Refs stay 1:1 with elements; delta snapshots track each row independently.
Positional fallback (T8) If nothing can disambiguate (no testid, no unique name, no nameable row), it emits a positional XPath (…)[n] marked low. Still resolves to one element — but surfaced as low-confidence so a human can add a test-id.
Uniqueness always comes from the derived locator, never from coercion. .or(), .filter(), .first(), .nth(), .last() as “make-it-unique” workarounds are forbidden (see §06).

04Dynamic IDs & data tables

“Dynamic id” means two very different things. Vindicate handles each in a different place — one is rejected automatically at capture, the other is an explicit author decision.

Case A — a generated id on the element (auto-rejected at tier T3)

Before T3 will use an id, isGeneratedDomId() checks whether it looks machine-generated. If so the id is discarded and the ladder falls through — a value like id="del-7f3a91" never becomes a locator.

The data-table walk-through

A products table where every row’s Delete button carries a different generated id:

<tr> <td>Product ABC</td> … <button id="del-7f3a91">Delete</button> </tr>
<tr> <td>Product XYZ</td> … <button id="del-0c92ab">Delete</button> </tr>
TierOutcome for the first Delete button
T1/T2No test-id → skip.
T3del-7f3a91 matches the hex-hash pattern → rejected.
T4role button + name Delete, but roleNameUnique is false (every row repeats it) → skip (won’t emit an ambiguous locator).
T7Wins. Scopes to the nearest repeating-row ancestor with a unique name (Product ABC); the colliding ref is re-digested with that row anchor.
 
// the dynamic id is simply ignored — anchor to the stable, human-meaningful row
getByRole('row', { name: 'Product ABC' })
  .getByRole('button', { name: 'Delete', exact: true })
If even the row has no unique name, it falls to T8 → positional (//button)[2] marked low and surfaced for review. The dynamic id is never used to disambiguate.

Case B — the value you’re searching for is runtime-driven (dyn_param)

Different problem: you’re not locating “the Delete in Product ABC’s row,” you’re locating “the Delete for whatever product id this test just created.” That is a genuinely parameterized locator, declared by the author — handled at authoring time, not capture.

// locator-helper: dyn_param   — declared dynamic with a {param}, codegen emits the method
private deleteButton(productId: string): Locator {
  return this.page.locator(`//button[@data-product-id="${productId}"]`);
}
// called inside a step_*:  await this.deleteButton(id).click();
Use dyn_param only when the value is truly runtime-driven. In a codegen schema you declare the element dynamic with a {param} placeholder (e.g. delete-product-{id}) and pass refArgs. Any loop or branch lives inside the page/panel method — never in the spec.

06The live-region exception (alert / status / log)

An ARIA name-from-content rule that trips up hand-written selectors — and the one place a naive “role + visible text” derivation is wrong.

✗ Wrong
getByRole('alert', { name: 'Invalid credentials' })

An alert/status/log takes its accessible name from author markup (aria-label), not its text. Its visible message is content, so the computed name is empty — this matches nothing.
✓ Right
getByRole('alert') + a verify_* with toContainText('Invalid credentials')

Locate the live region by role alone (tier T4b → role-only role_name, low), then assert its message as text. browser_read tags these with “assert text with toContainText.”

This is enforced at the source (capture refuses to bind content as a role name for these roles), defended again in codegen (a name-prohibited denylist), and documented in the skill so hand-authored .ts edits follow the same rule.

08Why this is the best approach

The design optimises for the two things that matter in long-lived test suites: resilience to change and trustworthiness of every selector.

PropertyHow the strategy delivers it
ResilientThe ladder prefers contract-grade identities (test-id, id) and semantic ones (role + accessible name) that survive restyles, re-layouts and DOM churn. Brittle positional locators are last and flagged.
Verified, not guessedEvery tier proves exactly-one-match against the real DOM at capture time. A locator that can’t be uniquely resolved never ships — there are no “probably works” selectors.
One source of truthA single StructuredLocator feeds codegen, the live resolver, and the browser_read badge. They cannot disagree: what the agent is shown is exactly what runs and exactly what is generated.
Human-readable outputGenerated page objects read like intent — getByRole('button',{name:'Sign in'}), not div.css-1x7y > button:nth-child(2). Reviewers and AI agents both navigate it instantly.
Honest about ambiguityDuplicates are resolved structurally (scoping, re-digested refs) or surfaced as low confidence — never silently swallowed by .first().
Accessibility-alignedBecause it locates the way a screen reader perceives the page (role + accessible name), the tests double as a soft a11y check and respect ARIA rules like name-from-content.
No invention surfaceThe agent can’t hallucinate a selector — it only supplies captured identity. This removes the single biggest source of flaky, wrong, or made-up locators in AI-authored tests.
In one line: capture identity once, derive the most durable unique locator the DOM actually supports, verify it on the spot, and render that one truth everywhere — semantic when possible, positional only when forced, and always honest about confidence.
