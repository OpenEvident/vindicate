02 Component Responsibilities
Process 1 of 3
Vindicate Extension
apps/vscode-extension · runs in VS Code & Cursor
  • Onboarding UI, dashboard/sidebar/panel webviews, file-watching for project health metrics
  • Spawns and supervises runtime-worker and runtime-mcp as local child processes
  • Detects installed AI tools (Cursor, VS Code/Copilot, Claude Code) and writes their MCP config files
  • One copy runs per open editor window — but coordinates through the shared worker/MCP rather than owning them
Process 2 of 3
runtime-mcp
apps/runtime-mcp · :9223
  • The MCP server the agent actually connects to — stateless between tool calls by design
  • One session per client connection, bound to that client's project_root — how one process safely serves several projects
  • Proxies browser/recording calls to the worker via WorkerClient (circuit breaker: healthy → degraded → down)
  • Serves the bundled workflow content graph (vindicate_workflow) and writes codegen/scaffold output directly to disk
Process 3 of 3
runtime-worker
apps/runtime-worker · :9121
  • Owns all real browser interaction via Playwright — sessions, commands, snapshots, recordings
  • Sessions move through a state machine: active → paused → dead → expired → closed, persisted to ~/.vindicate/sessions
  • Session-scoped file I/O resolves against that session's own project_root — never a process-wide setting
  • Idle self-shutdown after 5 min with no health pings and zero active sessions — nothing else tells it to stop
03 Process Lifecycle — Spawn, Attach, Share two editors, one worker

Editor B
read ~/.vindicate/worker.key — same key
→
probe GET /health — already running
→
probe /capabilities — key accepted
→
attaches — no new process
Every editor previously generated its own random key in VS Code's per-editor secret storage — not shared across editor apps or profiles, so a second editor always collided with the first ("already listening… with a different internal key"). The key now lives in one file, 0600 permissions, created atomically so two simultaneous first-launches can't race into two different keys.
Signing out or closing one editor window does not kill the shared worker — its lifetime is governed by idle self-shutdown instead (previous behavior force-killed it, breaking every other open editor). If two editors launch at the exact same moment and both attempt to spawn, the loser re-probes and attaches to the winner rather than surfacing an error.
04 Internal Authentication & Multi-Project Isolation
Internal Key — Local Only
  • There is exactly one auth mechanism here — no cloud account, no sign-in, no user identity anywhere
  • 32-byte hex value in ~/.vindicate/worker.key, sent as x-vindicate-internal-key
  • Stops arbitrary local processes or web pages from driving the worker (CSRF on localhost:9121) — proves the request came from this machine's own Vindicate install, nothing more
  • The MCP's own /mcp endpoint isn't gated by it at all
Isolation is per-request, not per-process. The extension bakes each project's absolute folder into its MCP URL (?project_root=...). runtime-mcp builds a fresh session + ProjectFs per client connection, scoped to that folder. Browser sessions carry project_root at creation and the worker reads it back from the session record for every later file/recording call — never from a worker-level setting. The agent never sees or sets project_root itself; it's a connection property the extension wires into the config file.

09 Known Operational Characteristics
No supervised auto-restart. If either process crashes, nothing currently restarts it automatically — the extension's health ping (every 30s) shows it as down, and the user must reload the editor window. Both processes now install unhandledRejection/uncaughtException handlers so a stray rejection logs and keeps the process alive instead of silently dying — previously the most common real-world cause of unexpected crashes mid-task.
One-time clean restart required on this shared-key change. Any worker spawned by a pre-update extension uses the old per-editor key scheme and won't be recognized by an updated extension — a full editor quit (not just "Reload Window") clears it. One-time only.
Multi-root workspaces — Vindicate uses only the first folder; a warning is logged if more than one is present.
Claude Desktop is not currently supported as an onboarding/pairing target — removed, since it has no workspace concept, which doesn't fit the per-session project_root model.
